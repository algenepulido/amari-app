# External reviewer threat model

Prepared 21 September 2026 against commit `d51fe55`. Every finding below was read from the
repository and carries a file and line reference. Nothing was verified against the production
database, and the live state of the data is marked unverified wherever it matters.

No credential value is reproduced in this document.

## What is being protected

The real member population and their contact details. The administrative surface, which can
change tiers, create invitation codes, publish content, manage events and check people in at
the door. The production database itself. The Apple and Google Play distribution accounts. The
signing material. The reputation cost of an incident involving people who attend AMARI events.

## Who the adversary is

Eight external developers who have not been engaged, who are being assessed, and who are being
invited precisely because they are capable of finding weaknesses. The brief is correct to treat
them as hostile. They will have a build of the application, a reviewer credential, and an
ordinary reason to explore. Anything reachable from the application is reachable by them.

The second adversary is anyone at all, because two of the findings below need no reviewer
credential and no account.

## Findings in the application as it stands

These are not risks created by the reviewer programme. They exist now, in production, and they
are the reason the programme cannot proceed against production.

### Finding one, a path from stranger to administrator

Severity critical. Confidence high on the code path, unverified on the live data.

The current bootstrap invitation pool is inserted from literal values generated by a predictable
pattern at `supabase/migrations/20260323000001_membership_invites_and_moderation.sql:962`.
Twelve of those codes carry an administrative grant at laureate tier, under two fixed prefixes
followed by a three digit counter. They were created with a one year expiry on 23 March 2026 and
therefore remain valid until March 2027 unless they have been redeemed or expired by hand.

`validate_invitation_code` is security definer and granted to the anonymous role at
`supabase/migrations/20260504000007_invite_validation_rate_limit_fix.sql:36`. That migration
removed the rate limit and did not replace it. A search of every migration confirms
`check_rate_limit` is now called from nowhere in the live schema. An unauthenticated caller
holding only the anonymous key, which ships inside the application and is committed at
`eas.json:50`, can therefore test the twelve administrative codes in twelve requests and learn
which remain unused.

`redeem_invitation_code` is security definer and granted to the authenticated role at
`supabase/migrations/20260521000002_retire_duplicate_member_invites.sql:134`. Account creation
is open through Apple, Google and email. When the invitation carries an administrative grant the
function inserts a row into `admin_roles` and writes the administrative flag into the
authentication metadata, at lines 102 and 112.

`public.is_admin()` reads `admin_roles` at
`supabase/migrations/20260321000003_authority_hardening_v2.sql:28`, and the custom access token
hook mints the claim from the same table. Every administrative policy and every administrative
function then passes.

The only thing standing between an attacker and this outcome is whether all twelve codes have
already been redeemed. That is unverified, and an already-redeemed code is a coincidence, not a
control.

### Finding two, redemption trusts caller-supplied identity

Severity high.

`redeem_invitation_code` accepts `p_user_id uuid` from the caller and never compares it with
`auth.uid()`, at `supabase/migrations/20260521000002_retire_duplicate_member_invites.sql:3`.
The member row, the administrative role and the authentication metadata are all bound to
whatever identifier the caller sends. The project's own security roadmap sets the opposite
standard at `docs/SECURITY-HARDENING-ROADMAP.md:55`, requiring functions that accept user
identifiers to prove `auth.uid()` matches or to require administrative rights.

### Finding three, the Apple relay exception is not conditioned on Apple

Severity high.

An invitation may be bound to a recipient email. That binding is skipped for any address ending
in the Apple private relay domain, at
`supabase/migrations/20260521000002_retire_duplicate_member_invites.sql:60`. The check tests the
shape of a caller-supplied string, not the authentication provider. A caller signed in with
Google or with an email code can supply such an address and bypass the only binding control on
an invitation code.

### Finding four, a committed live invitation code and personal data

Severity high.

A real production invitation code at silver tier, together with a named individual's email
address, is committed in plain text in `scripts/verify-mobile-flows.mjs:37` and repeated in
`docs/TINASHE-ANDROID-TEST-SCRIPT.md`. Unlike the bootstrap pool this code is not predictable,
which makes it stronger against guessing and weaker against anyone with repository access,
because no guessing is required. It should be expired regardless of whether it has been used.

`supabase/seed.sql:7` also contains four literal invitation codes, one of which grants laureate
tier with administrative rights. The file is headed as development test data. Whether it has
ever been applied to the production project is unverified.

### Finding five, the rate limit that was documented as present is absent

Severity medium, and material because it is a regression against a stated control.

`docs/SECURITY-HARDENING-ROADMAP.md:25` records invite-code rate limiting as a current security
foundation. It was removed six days after that document was written. No rate limiting is in
force anywhere in the schema today.

### Finding six, twelve security definer functions keep the default public grant

Severity medium.

There is no blanket revoke and no altered default privileges in the schema, so any function
never named in a revoke statement keeps the Postgres default of execute to public. Twelve
security definer functions are in that position and are ordinary callable functions rather than
trigger functions. Two consequences matter. `check_rate_limit`, at
`supabase/migrations/20260301000000_initial_schema.sql:633`, lets any caller insert arbitrary
rows into the rate limit table and sets no search path. The three map functions, at
`supabase/migrations/20260326000001_map_feature.sql:159`, `:184` and `:217`, return project
name, description, category, creator first name, image, link and coordinates for any bounding
box, with no membership check, to anyone holding the anonymous key. Project locations are
coarsened to a region centroid by a trigger, so the coordinates are not precise, but the records
themselves are world readable.

### Finding seven, the signing password is an unmasked workflow input

Severity medium.

`.github/workflows/setup-keystore.yml:4` declares the keystore password as a workflow dispatch
input of type string, which is not masked in run metadata, and lines 35 to 42 upload both the
keystore and its base64 encoding as a build artefact. Anyone with read access to that run can
retrieve both halves.

### Finding eight, the security gate has never looked at the database

Severity medium, and the reason several of the findings above survived.

`scripts/verify-security.mjs:5` scans `app`, `components`, `hooks`, `lib`, `providers` and
`queries`. It has never scanned `supabase/migrations`. No gate in the repository inspects
function grants, security definer attributes, search paths or seeded credentials, which is
precisely where the critical finding lives.

### Finding nine, suspended members are not rejected by the client guard

Severity low on its own, unverified on the server side.

The root guard reads the member status and does not act on it, at `app/_layout.tsx:65`. Whether
the database refuses a suspended member is unverified and should be tested rather than assumed.

## Threats introduced by the reviewer programme itself

These would apply even after the findings above were remediated.

**A reviewer reaches real member data.** Mitigated only by running in an isolated environment
with synthetic data. In production the member table is self-read only, but
`get_aligned_tile_contact_details` returns a real owner's email to an eligible member, and the
map functions return creator first names to anyone. Isolation removes the class; tier gating
alone does not.

**A reviewer escalates privilege.** Mitigated by a reviewer activation path that cannot write a
tier, cannot write to `admin_roles` and cannot write authentication metadata, and by proving
that with tests that must fail rather than tests that pass.

**A reviewer outlives their window.** Mitigated by evaluating expiry in the database on every
reviewer-reachable path. A client that hides content is not an expiry mechanism, and a session
that is still valid after the slot expires is the failure this control exists to prevent.

**A reviewer activates a slot from a platform other than iOS.** Mitigated by reading
`auth.identities` server side. Not mitigated by any check on `Platform.OS`, which the client
controls. This is the one control in the design that rests on behaviour not yet demonstrated
anywhere in this repository, and it must be proven by a negative test before it is relied upon.

**A reviewer disturbs live operations.** In an isolated environment, no production push, no
production email, no production analytics and no production recommendation input is reachable at
all. In production the opposite is true: an ordinary member can already cause a push to every
administrator by reporting an issue.

**A reviewer shares their credential.** Mitigated by single use binding to the first identity,
by short expiry and by the audit log. Not fully preventable, which is why the credential must be
worth little.

**Two reviewers redeem the same code at the same moment.** Mitigated by row locking inside one
transaction.

## Residual risk under the proposed design

An isolated environment removes the data risk and the operational risk, and leaves three things
standing.

A reviewer can still probe the reviewer environment's authorisation layer and find defects in
it. That is acceptable, and arguably useful, provided the environment shares no data and no
credentials with production.

A reviewer learns the application's structure, its function names and its shapes, which
transfers to production even though the data does not. This is inherent in showing anyone the
product and is accepted.

The Apple-only control depends on server-side provider inspection that has not yet been
demonstrated in this codebase. Until the negative test passes, the Apple-only claim should be
described as intended rather than enforced.

## What must happen before the programme proceeds

The findings in this document are not preconditions invented by the reviewer programme. They are
the reason the programme cannot use production. Findings one through four should be treated as
an incident on their own timetable, independently of whether any reviewer is ever onboarded.

The first step for finding one is a single read-only query that reveals no code value, counting
how many administrative bootstrap codes remain unused and unexpired. If that count is above
zero, the remedy is a migration that expires those rows, which removes access without deleting
history.
